# Developer Portal dark-mode plan

Status: implemented and browser-reviewed, 2026-09-13, on `codex/portal-dark-mode` in the separate `developer-portal-dark-mode` worktree, based on `origin/main` (`2f18f7b17`). Prepared for draft review; not released. Figma content has not been changed. See [QA report](qa-report.md) for actual coverage and remaining limitations, including the open top-switcher artifact report.

## Recommendation: best balance of polish and regression risk

Use semantic CSS variables with a small, deliberate dark palette derived from the Figma primitives. Preserve the original light palette, migrate shared components by role, and activate dark mode behind a flag after their consumers are covered. This remains the recommended balance for this repository after browser review: neutral elevation, readable interactions, and selective icon recoloring without inverting brand artwork. It is not a guarantee of zero regressions or an objective aesthetic optimum.

| Approach                                                        | Visual quality                                                              | Change risk / maintenance                                             | Verdict                                         |
| --------------------------------------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------- |
| Global inversion filter or global reversal of grey/white tokens | Distorts brand assets and collapses unrelated roles                         | Few edits but broad, unpredictable impact                             | Avoid                                           |
| Add dark: classes to every color occurrence                     | Can be polished with enough hand tuning                                     | Duplicated state rules and easy omissions across legacy/shared UI     | Reserve for isolated exceptions                 |
| Strict one-for-one Figma primitive aliases                      | Consistent source provenance, but sparse dark elevation and specialty tints | Semantic migration is safe; automatic swaps still collide             | Useful fallback if derived colors are forbidden |
| Semantic roles + three derived neutral surfaces                 | Subtle neutral elevation, controlled contrast, preserved accents            | Moderate initial migration; centralized tuning and reversible rollout | Recommended                                     |

The original strict-palette proposal is retained in strict-primitive-mapping.json. The recommended semantic-mapping.json adds only three derived dark surfaces. These are design proposals, not tokens claimed to exist in Figma. Precompute their hex values so runtime styling does not depend on color-mix support. Reuse the portal's existing semantic and shadcn infrastructure; a new component library or redesign is unnecessary.

## Evidence and deliverables

The [UI Kit 4.0 Color primitives page](https://www.figma.com/design/rQyitWCsRVKHsR26qsZHdX/UI-Kit-4.0?node-id=4-3) exposes named paint styles, not a ready-made light/dark variable collection. The Figma plugin returned zero local COLOR variables. Extracted 57 Primary/Specialty styles plus 18 token-identity styles. The separate 4.1 WIP pages are outside this proposal.

- [figma-primitives.json](figma-primitives.json): exact style names, IDs, hex values, and source provenance. Tokens/\* identifies currencies/assets, not generic UI semantic roles.
- [portal-colors.json](portal-colors.json): requested color array. 591 entries from 949 tracked frontend files, including 181 definitions, 147 literal spellings, 29 SVG literal spellings, 230 utility forms, and 4 named literals. Entries overlap in rendered color; this is not 591 unique RGB values. Each includes counts, up to three source references, nearest Figma primitive, calculated tonal opposite, and review status.
- [token-candidates.md](token-candidates.md): compact mapping of the portal's custom literal color tokens.
- [semantic-mapping.json](semantic-mapping.json): 25 recommended mappings by UI role, including three explicitly documented derived surfaces, overriding numerical candidates where necessary.
- [contrast-checks.json](contrast-checks.json): 25 calculated checks for selected opaque semantic pairs; all pass their stated thresholds.
- [audit-summary.json](audit-summary.json) and [audit-colors.mjs](audit-colors.mjs): scope, limitations, and reproducible static scanner. Run `node docs/dark-mode/audit-colors.mjs` from `web/`; it emits the inventory and metadata to stdout without changing files.

The scan covers tracked app/components/scenes/styles/lib/hooks/public TS, JS, CSS and SVG, including admin and legacy UI. It excludes generated files, tests, untracked work such as FedScreens, raster pixels, and external stylesheets. It is lexical, not route reachability or computed-style analysis. Dynamic classes, uploaded content, syntax-highlighter themes, arbitrary utility opacity, and composited gradients require runtime review. Literal hits in comments/example code may need dismissal.

## Mapping decisions

“Opposite” means a tonal counterpart within the nearest primitive family. The scanner measures Euclidean OKLab distance, reflects lightness around the family's observed minimum/maximum, and finds the closest existing stop while retaining a/b. This is a reproducible candidate generator, not evidence of designer-authored dark aliases. Alpha stays separate, transparent stays transparent, and currentColor stays inherited. Sparse specialty families and unresolved expressions are explicitly flagged.

Use semantic roles for implementation. For example, white card backgrounds should become dark surfaces, but white labels on a blue identity tile may need to stay white. `portal-ink` currently appears in both text and button backgrounds; split those usages before changing its value. Purple and green remain purple and green even if a nearest-neighbor match drifts toward another family.

| Role                        | Current example         | Proposed dark primitive               | Value             |
| --------------------------- | ----------------------- | ------------------------------------- | ----------------- |
| Canvas                      | portal-canvas           | Primary/Grey/900                      | #181818           |
| Base cards                  | white                   | Derived: Grey/0 at 3% over Grey/900   | #1F1F1F           |
| Raised menus/dialogs        | white                   | Derived: Grey/0 at 6.5% over Grey/900 | #272727           |
| Hover/selected surface      | pale grey               | Derived: Grey/0 at 10% over Grey/900  | #2F2F2F           |
| Main text                   | portal-text / grey-900  | Primary/Grey/50                       | #F9FAFB           |
| Supporting text             | portal-muted / grey-500 | Primary/Grey/400                      | #9BA3AE           |
| Decorative divider          | portal-border           | Primary/Grey/700                      | #3C424B           |
| Required control boundary   | grey-200                | Primary/Grey/450                      | #838D9B           |
| Primary action fill / label | ink / white             | Grey/0 / Grey/900                     | #FFFFFF / #181818 |
| Link                        | portal-blue             | Primary/Info/400                      | #66A3FF           |
| Focus indicator             | accent-ring             | Primary/Info/300                      | #99C2FF           |
| Info fill / text            | pale blue / blue        | Info/900 / Info/300                   | #002466 / #99C2FF |
| Error fill / text           | pale red / red          | Error/900 / Error/400                 | #611005 / #F97B6F |
| Success fill / text         | pale green / green      | Success/900 / Success/300             | #004D13 / #99E8B3 |
| Warning fill / text         | pale amber / amber      | Warning/900 / Warning/300             | #664600 / #FFDB99 |

The derived values are rounded 8-bit sRGB blends of two real Figma primitives. They provide distinct canvas, card, raised, and interaction layers without the large jump to Grey/700. Neutral surfaces also fit the portal's existing #181818/#1F1F1F ink palette. Keep accent saturation for actions, statuses and data; avoid making every surface colored or relying on large shadows. Use subtle decorative borders where needed and stronger boundaries for controls.

The strict palette's Grey/400 text only achieves 3.98:1 on Grey/700. On the recommended #272727 raised surface it achieves 5.864:1, and 5.256:1 on #2F2F2F hover. This permits a calmer supporting-text color without losing normal-text contrast. Info/600 (#005CFF) remains only 3.36:1 on the canvas, so retain it for suitable brand/fill roles instead of small dark-mode link text. Grey/700 decorative borders are not sufficient as sole control boundaries; use Grey/450 for those. Use [WCAG 2.2](https://www.w3.org/TR/WCAG22/) thresholds of 4.5:1 for normal text and 3:1 for applicable large text/non-text indicators, checking actual adjacent and composited pairs.

## Implementation sequence

1. **Introduce primitive and semantic layers, retaining current light values.** Add a dedicated theme stylesheet imported from `styles/globals.css`. Keep fixed Figma primitives immutable. Add roles for canvas/card/raised/hover, text/secondary/disabled, decorative/control borders, action fill/label, focus, statuses, charts and overlays. Alias Tailwind v4 utilities through `@theme inline` to semantic variables; switch semantic values under `.dark`. Connect existing shadcn `--background`, `--card`, `--primary`, `--sidebar-*`, etc. to the same roles. Existing `.dark` definitions only cover that semantic subset; legacy `grey-*`, `system-*`, portal tokens and hardcoded colors currently stay light. Avoid globally reversing the primitive scales.

2. **Add Light / Dark / System preference and initialization.** Prefer a thin `next-themes` integration (a new dependency, not currently installed) with `scenes/Root/layout/index.tsx` and the portal profile/account controls. Resolve explicit preference before system preference, update on OS changes only in System mode, persist a validated enum, and synchronize tabs. Set the root `.dark` class and CSS `color-scheme` before first paint. Follow [Tailwind's system-theme approach](https://tailwindcss.com/docs/dark-mode#with-system-theme-support), but pass the existing per-request `x-nonce` from `proxy.ts` to the initialization script so CSP permits it. Use the library's class strategy, system support, theme storage and nonce prop; scope `suppressHydrationWarning` to the root html attribute change and defer only theme-dependent control labels until mounted. Its [official documentation](https://github.com/pacocoursey/next-themes) covers these integration points. Avoid a second handwritten bootstrap competing with its injected script. Add a narrow enum-validation boundary and verify malformed/blocked storage behavior, OS updates and tab sync against the selected version. Wire forced light to the rollout/route gate. A small Jotai controller is a dependency-free alternative, but it duplicates preference/initialization edge cases and is not the default recommendation.

3. **Migrate shared components and the active portal shell.** Start with `scenes/PortalV3/layout/Shell`, shared `components/ui`, Button/Input/Select/DialogOverlay, `scenes/PortalV3/common/InkButton`, settings panels and status treatments. Map each usage by property and role. Inventory priorities include text-grey-500 (230 occurrences), text-grey-900 (225), border-grey-200 (131), bg-white (69), and bg-grey-0 (58); counts are static across the audited scope. Map required placeholder/help text to readable supporting text, and reserve disabled colors for inactive controls. Set semantic foregrounds explicitly, including button labels, icons, focus-ring offsets and portaled menus.

4. **Migrate page and rendering exceptions.** Cover apps, World ID/actions, credentials, settings/profile, notifications and analytics, then onboarding/error pages and any admin routes sharing root theme state. Audit `MetricsFrame/DailyMetricChart.tsx` (grid, ticks, tooltip and white strokes), `TotalsFunnel.tsx` (series array and background track), other chart configurations, and `components/CodeBlock` including the external syntax theme. React SVG charts can use CSS variables; canvas charts must resolve computed colors and redraw on theme changes. Preserve series/category identity and distinguish them beyond color. Replace fixed Root `SkeletonTheme` values and Toastify border/background/text values. Review masks, shadows, gradients, image backplates, QR codes, avatars from `additionalColors`/`calculateColorFromString`, and `PlaceholderImage`. Preserve QR contrast and brand/uploaded-image colors; do not automatically invert raster assets or mask colors. The per-user `colorAtom` is an accent choice, not the new mode state.

5. **Verify before exposing the switch.** Test first load, explicit/system preference precedence, OS change, malformed/blocked storage, reload, tab sync, CSP and hydration. Capture real screenshots at mobile (390 px) and desktop (1440 px), both modes, for shell/apps, forms, menus, dialogs, errors, empty/loading states, notifications and charts. Include hover, selected, keyboard focus, disabled, invalid, and chart tooltip states. Run rendered contrast/keyboard checks, then `pnpm format:check`, `pnpm exec tsc --noEmit`, required linters, and relevant existing tests. Add focused tests for theme state branches and browser coverage where behavior warrants them. Resolve newly found raw colors and semantic collisions before declaring coverage complete.

6. **Release in reversible stages.** Land token infrastructure with light mode unchanged, then component/page migrations, then the preference control. Gate activation using the existing feature-flag infrastructure, beginning internally and expanding after visual review. The gate must control bootstrap and controller consistently; rollback forces light and hides the option while retaining stored preference. Keep unaudited admin/onboarding routes explicitly light until they are migrated, including portal-mounted overlays. Reuse existing frontend error tracking for initialization failures and correlate regressions with release/flag state; avoid per-render logging or a new backend service for theme state.

## Current validation and open design work

Agent-run: Figma primitive extraction and original inventory; local implementation; Chrome desktop and 390px mobile click-through; computed-style contrast spot checks; 15 tests against actual dark CSS token pairs; 900 passing unit/schema/script tests; passing typecheck, lint, and repository formatting. Full details and screenshots are in [qa-report.md](qa-report.md).

The inventory and mapping JSON files preserve the original planning snapshot; `styles/portal-theme.css` is the implementation source of truth. In particular, raised-menu hover uses `#3c424b` so it is visibly distinct from the `#272727` menu, rather than reusing the subtler card hover. Marketing, onboarding, admin and kiosk routes remain forced light. Production is off by default; `PORTAL_DARK_MODE_ENABLED=true` opts in, and explicit `false` forces light even in development.

Registered-RP and Mini App-only workflows were unavailable in the supplied account; transactions showed an upstream failure. Shared charts and controls were therefore also checked using synthetic, development-only `/theme-preview` content. OS preference changes, cross-tab synchronization, production CSP/hydration and non-Chrome browsers still need release QA. Existing low-contrast light-mode supporting text and avatar colors were not globally redesigned. Do not interpret this pass as every possible site state being certified perfect.
